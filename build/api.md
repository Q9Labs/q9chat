# Q9 Chat v1: public Convex API

Source of truth for the data model: `convex/schema.ts`. Function results are display-ready (names, avatar colors, file routes) and declared with return validators that mirror the schema's unions, so both apps stay thin.

## Who may call what

Every function belongs to exactly one class, enforced by one helper per class in `convex/lib/access.ts`. No function picks its own rule.

| Class      | Caller must be                                                                                                                                    | Functions                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `anyone`   | anything, including signed out                                                                                                                    | `profiles.me`                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `identity` | signed in, with or without a profile                                                                                                              | `profiles.setUp` (an action that first confirms with WorkOS that the token's user still exists)                                                                                                                                                                                                                                                                                                                                                       |
| `active`   | signed in with an `active` profile                                                                                                                | `groups.list`, `groups.create`, `groups.pairWith`, `groups.openPair`, `groups.inviteInfo`, `groups.join`, `groups.leave` (own membership; a no-op when it's already gone), `groups.dismissRemoval` (own removal row only), `people.find`, `messages.search` (an action; each internal query it runs checks membership of every group it reads), `profiles.update`, `profiles.deleteAccount`, `devices.*` (own devices only), the `POST /upload` route |
| `member`   | `active`, and a membership row in the group the server resolves (from the message for message functions, never from a client-sent group id alone) | `groups.get`, `groups.addMembers`, `groups.removeMember`, `groups.setNotify`, `messages.range`, `messages.reactors`, `messages.send`, `messages.edit`, `messages.remove`, `messages.react`, `readStates.markRead`, `typing.*`, `reports.create`, the `GET /files/...` route                                                                                                                                                                           |

- A `deleting` or `deleted` profile fails every class except `anyone`, whatever its token or leftover rows say.
- Target people (added members, pair partners) must be `active` too.
- `groups.get` is the one `member` function with a fallback: a person with an undismissed removal row gets only the removal notice.
- Errors a person can cause and an app must show are `ConvexError`s with a `code` from one shared union: `not_member`, `not_author`, `removed_from_group`, `invite_invalid`, `name_required`, `name_too_long`, `pair_locked`, `account_unavailable`, `client_key_reused`, `message_too_long`, `bad_attachment` (type, size, count or voice rules), `group_full`, `too_many_groups`. Inputs the apps cap themselves (search query, client key, invite token, push subscription strings) fail with a plain error, because a correct app never sends them.

## Rules every function follows

- Sequences are gap-free per group and order its history; they address any range and find a message far back. They are not unread counts.
- Unread: each post inserts an `unreadPosts` row for every other member; member events and the author's own posts insert none. A post deleted later stays unread for whoever hadn't read it. Sending never marks anything read. `markRead` only moves forward and deletes the caller's rows up to the new position, in batches when there are many. A count reads at most 100 rows per group after the caller's `lastReadSequence` (the apps show "99+"), so its cost never depends on history. Leave and removal delete the membership and read state at once and schedule batch deletion of that person's unread rows up to the group's `lastSequence` at that moment; a re-add starts read at the current sequence, so leftover rows never count and a late cleanup never touches rows from the new membership.
- `readStates.lastNeedsYouSequence` records the latest post that mentioned the person or replied to them when it was sent; the "@" badge shows while it is after `lastReadSequence`. Edits and deletes don't change it.
- A person joining or created into a group starts read at the group's current last sequence.
- Author labels, typing and previews use the first word of `displayName`; member lists and the account screen use the full name. Every person in a result carries their `id` and `isYou`, so the apps never match people by name.
- A `deleting` or `deleted` account resolves to `{ name: "Deleted account", deleted: true }` everywhere, including a pair whose partner was deleted: pair partners come from `pairKey`, not from current membership.
- Mentions: the server finds them. An `@Word` token mentions every current member whose first name matches it, case-insensitively. Edits re-parse mentions and never notify.
- Limits, each with its own error: body up to 4,000 characters and not blank unless the post has attachments; up to 10 images or files per post; a voice note is a post of its own with an empty body, up to 10 minutes, with at most 64 waveform samples from 0 to 1; files up to 20 MB (our product cap, under Convex's 20 MiB HTTP body limit); file names up to 200 characters; image types JPEG, PNG, WebP and GIF, the formats every supported browser shows (a HEIC upload is a file, not an image, so the phone picks photos as JPEG); voice types AAC/M4A, WebM and Ogg, with the type taken from the container signature in the file's first bytes (JPEG, PNG, WebP, GIF; Ogg, WebM, MP4/M4A, ADTS AAC; HEIC brands are checked before MP4 so a HEIC is never taken for a voice note), never from the declared MIME. The server doesn't parse codecs, so a crafted file with a right signature that doesn't play shows as an unplayable voice note, which v1 accepts; image width and height are layout hints from the app, whole numbers from 1 to 8,000; display names up to 60 characters and group names up to 80; a group has at most 100 members (`group_full`); one `addMembers` call adds at most 50; a person belongs to at most 100 groups (`too_many_groups`); a range spans at most 100 sequences; search queries up to 100 characters; client keys up to 64 characters; invite tokens 16 to 32 base62 characters; web push endpoints up to 2,000 characters and keys up to 200. These caps are chosen so the worst case of every query below fits Convex's per-transaction limits (16 MiB read, 32,000 documents scanned, 4,096 index ranges).
- Files: uploads go to the authenticated `POST /upload` route on the Convex site, which checks size and type, stores the bytes and returns an `uploadId`. Sending a post or setting a photo consumes the upload, so it is used once and only by its uploader; a cron deletes uploads unused after a day. Storage ids never leave the server: the apps load bytes from `GET /files/{messageId}/{index}` (membership of the message's group checked on every request) and `GET /photos/{profileId}` (any `active` caller), sending the access token as a bearer header. So a former member can't fetch files again, and no file is shared by two messages. The route stores the bytes and then records the upload in a mutation that re-checks the caller is `active`; if that mutation fails, the route deletes the bytes. A crash between the two leaks one stored file, which v1 accepts. The File picker may consume any validated upload as a file, retaining the server-sniffed content type. Image and voice consumption must match the recorded kind. Ownership, size and single-use checks apply to every kind.

## Journey 1: sign in and land in your groups

- `profiles.me` → `null` when signed out; `{ status: "needsSetup" }` before the first profile exists (a query can't ask WorkOS, so the setup screen takes the email and suggested name from the sign-in session's `user`); `{ status: "ready", profile: { id, displayName, email, photo, color } }`; `{ status: "unavailable" }` for a deleting or deleted account.
- `profiles.setUp({ displayName })` (action) → confirms the token's user with WorkOS (refuses one that no longer exists), then creates the profile once (idempotent). Email and the suggested name come from WorkOS, never from the client. Trims the name and rejects blank. The setup screen's photo is uploaded right after, through `profiles.update`.
- `groups.list` → rows newest activity first, as a union: `{ status: "member", groupId, kind, title, avatar, lastActivityAt, preview, unreadCount, needsYou, notify }` or `{ status: "removed", groupId, kind, title, avatar, removedBy, removedAt }`. Removal notices are the caller's undismissed removal rows, read through the `(profileId, dismissedAt)` index; a person has at most 20, because a removal that would make a 21st dismisses the oldest. Dismissed rows stay as bans and `groups.list` never reads them, so its cost depends on the caller's current groups and 20 notices, not on their history. `preview` is structured: `{ by: { id, name, isYou } | null, summary }` with summary one of text, "Photo", the file name, "Voice note", "Message deleted", or an event that names at most three people, as in the timeline. The app renders "You: …", "Bilal: …", no prefix in pairs, and event sentences.
- "Signed in with Google / Email code / Apple" comes from the sign-in session, not from Convex.

## Journey 2: create a group, add people, start a group of two

- `people.find({ query })` → up to four `{ id, name, fullName, email, avatar }`, where `email` is set only on an exact email match (the person typed it) and is null for a name match, so joining a group by link never reveals its members' addresses. A name prefix (the start of any word of the name) matches only people who share a group with the caller; anyone else matches only by exact email. This keeps open sign-up from exposing a directory. The name match reads the caller's memberships and each of those groups' member rows, which carry the member's lowercase `searchName`, so its worst case is 100 groups of 100 rows and it reads profiles only for the four results. `profiles.update` rewrites `searchName` on the person's memberships when the name changes.
- `groups.create({ name?, memberIds, inviteToken })` → groupId. The New group form shows its link before the group exists, so the app generates the token (16 base62 characters from `crypto.getRandomValues`) and the server checks its format and that it is unused. Name defaults to the joined first names when people are given; a blank name with no people is rejected (`name_required`). Writes "created" and, if people were given, one "added" event listing them all.
- `groups.pairWith({ profileId })` → existing pair groupId or `null` ("Start" versus "Open").
- `groups.openPair({ profileId })` → the existing pair or a new one, created atomically with its key so two taps can't make two. The partner must be another `active` person.
- `groups.addMembers({ groupId, profileIds })` → deduplicates, skips people already in, writes one "added" event listing the people actually added, clears their removal rows. Rejected on pairs (`pair_locked`). A retry adds nobody twice.
- `groups.inviteInfo({ token })` → `{ status: "open", groupId, title, memberCount }`, `{ status: "member", groupId }`, `{ status: "removed" }` (nothing about the group), or `null`.
- `groups.join({ token })` → groupId; a no-op for a member. Writes a "joined" event. Refused with `removed_from_group` while a removal row exists.

## Journey 3: open a group and see what is new

- `groups.get({ groupId })` → `{ status: "member", groupId, kind, title, avatar, memberCount, members: [...], partner?, notify, inviteToken?, lastSequence, lastReadSequence, firstUnreadSequence }`, `{ status: "removed", title, avatar, memberCount, removedBy, removedAt }` (the mock's removed Group info shows the count), or `null`. `firstUnreadSequence` is the caller's oldest unread post in the group, or null, read as the first `unreadPosts` row through `by_profile_group_sequence`, so the app opens at the divider without walking history. The app captures `lastReadSequence` and `firstUnreadSequence` when it opens the group, so the "New since you last looked" divider stays put while `markRead` clears the badge.
- `messages.range({ groupId, fromSequence, toSequence })` → up to 100 messages in order, each a union on `kind`: post `{ id, sequence, createdAt, clientKey, author, body, mentions, attachments, replyTo, reactions, editedAt }`, deleted `{ id, sequence, createdAt, author }`, or event `{ id, sequence, createdAt, event }` with people resolved. `mentions` is the list of mentioned profile ids, not resolved people: the app highlights an `@Word` token when it matches the first name of a current member (from `groups.get`) and styles it as you when your id is in the list. An event names at most three people (`{ type: "added", by, people, othersCount }` renders as "Hasan added Bilal, Sara, Omar and 4 others"). One person cache serves the whole query, so a page costs at most about 800 lookups whatever its history. `attachments` carry their file route and metadata; `replyTo` is `{ id, sequence, author, summary } | { id, sequence, author, deleted: true }`; `reactions` are per emoji `{ emoji, count, mine }`, from the post's `reactionCounts` plus one lookup of the caller's own reaction. It reads only membership and the messages, quotes, the caller's reactions and the profiles it returns, never the group document or read state, so old pages don't re-run on every send, and its cost doesn't depend on how many people ever reacted.
- `messages.reactors({ messageId })` → per emoji `{ emoji, count, people: [{ id, name, isYou }] }` with at most 10 people each, read through the `(messageId, emoji)` index. The web tooltip ("Hasan and Sara reacted with 👍", or "Hasan, Sara and 12 others…" past 10) and the phone Reactions sheet load it when they open.
- `readStates.markRead({ groupId, sequence })` → validates the sequence exists in the group, moves forward only. The apps call it for messages that were on screen in a focused window.

## Journey 4: send text, an image, a file or a voice note

- `POST /upload` (HTTP route) → `{ uploadId }`.
- `messages.send({ groupId, clientKey, body, replyToId?, attachments: [{ uploadId, kind, name?, width?, height?, durationMs?, waveform? }] })` → `{ messageId, sequence }`. Looks up `(author, clientKey)` first: a retry returns the committed message unchanged (even if since edited or deleted) and schedules nothing new; the same key with a different group fails with `client_key_reused`. Only then does it check content and consume the uploads. A reply target must be a post or a deleted post in the same group, never an event. Bumps `lastSequence`, inserts unread rows for other members, records "needs you" for mentioned and replied-to members, and schedules notification delivery.
- The apps keep pending sends (with their client keys and the files' bytes) on the device, so a retry after a restart still deduplicates, and an upload that expired is uploaded again under the same client key.

## Journey 5: reply by quoting and jump to the original

- `messages.send({ replyToId })` checks the original is in the same group. The reply's `replyTo.sequence` lets the app ask `messages.range` for a window around the original.

## Journey 6: edit, delete, react, typing

- `messages.edit({ messageId, body })` → author only; text-only posts only (no attachments); the new body must not be blank; sets `editedAt`.
- `messages.remove({ messageId })` → author only; turns the post into the deleted placeholder, which has no reaction counts, so its reactions disappear at once; deletes its files; and schedules batch deletion of its reaction rows. Idempotent.
- `messages.react({ messageId, emoji })` → sets, replaces or clears (`emoji: null`) the caller's one reaction on a post, and updates the post's `reactionCounts` in the same mutation. People who leave a group keep their reactions; account deletion removes them and lowers the counts.
- `typing.start({ groupId })` → upserts the caller's row with `expiresAt` a few seconds ahead; `typing.stop({ groupId })` deletes it. With two devices, one device stopping clears the person's typing early; that is accepted.
- `typing.list({ groupId })` → `[{ id, name, expiresAt }]` for other current members. A cron deletes expired rows.
- Arrow-up edits the last own text post among the loaded messages.

## Journey 7: search

- `messages.search({ query, groupId? })` (action) → up to 50 hits: `{ groupId, groupTitle, sequence, author, createdAt, snippet }`, newest first among the best matches. It reads the caller's group ids, then runs one internal query per batch of 10 groups in parallel; each re-checks membership of its groups and takes the 10 most relevant matches per group, so one batch reads at most 100 posts (about 1 MB). It merges the batches and sorts by time, so a group with more than 10 matches shows its 10 most relevant. Results are a snapshot taken when the query runs, not live; the app runs it again as the query changes. It matches whole words and the start of the last word typed ("Test" finds "TestFlight"), not text inside a word. Deleted posts and events have no search text; voice notes have none.

## Journey 8: notifications

- `devices.registerExpo({ expoPushToken })`, `devices.registerWeb({ endpoint, p256dh, auth })` → upsert by token or endpoint and move it to the caller, clearing any `viewing` record, so a shared device follows the account signed in on it. `devices.unregister(...)` runs on sign-out. `devices.viewing` and `devices.unregister` change only a device the caller owns; a token or endpoint alone authorizes nothing. A person has at most 10 devices; registering an 11th drops the oldest.
- Delivery is an internal Effect action scheduled by `send`. Right before dispatch it re-reads the recipient's membership, notify mode, account status and devices, and skips anyone no longer eligible. Rule: a mention of the person or a reply to them notifies unless the group is muted; "all" notifies every post; the author is never notified.
- Foreground suppression. Phone: the app's notification handler doesn't present a notification for the chat on screen (native apps may stay silent). Web: browsers must show every push they receive, so the server decides. A focused tab calls `devices.viewing({ endpoint, groupId | null })` when it shows a group and every 30 seconds while it stays focused; the record expires after 60 seconds and is visible to nobody else. Delivery skips a web device whose record shows the message's group. A tab sends `null` when it loses focus or hides; a tab that closes without that stops renewing, so it can suppress notifications for that group for up to 60 seconds. The record is per browser and the last write wins, so a late clear from another tab can cost the focused tab one extra notification until its next renewal, at most 30 seconds later. Foreground detection is close to exact, not exact.
- The notification text is the group title, the author's first name and the first 200 characters of the body (cut on a character boundary, with "…"), so the worst-case payload stays well under the 4 KB limits of Expo and Web Push.
- Every delivery attempt, including a retry after a provider error, re-reads eligibility right before it sends. An Expo ticket with `DeviceNotRegistered`, or a Web Push 404 or 410, deletes that device if it still belongs to the same person.
- The payload opens the group at the message: `/g/{groupId}?m={sequence}` on web and the same path through the app's `q9chat://` link on the phone. Once a push provider has accepted a notification it can't be recalled.

## Journey 9: mute, leave, remove

- `groups.setNotify({ groupId, notify })` → "mentions" | "all" | "muted".
- `groups.leave({ groupId })` → deletes membership, read state and typing row, schedules the unread cleanup described under the rules, writes a "left" event. Rejected on pairs. A no-op, with no event and nothing about the group returned, when the caller isn't a member.
- `groups.removeMember({ groupId, profileId })` → any member, not on pairs, not oneself; deletes the target's membership, read state and typing row, schedules their unread cleanup, writes a "removed" event and a removal row (dismissing their oldest notice past 20). Idempotent.
- `groups.dismissRemoval({ groupId })` → sets `dismissedAt` on the caller's removal row. The row stays, so the invite link still can't bring them back; a member adding them deletes it.

## Store requirements

- `profiles.update({ displayName?, photoUploadId? | null })` → a new name must not be blank.
- `profiles.deleteAccount()` → in one mutation sets the profile to `deleting` (keeping the photo's storage id for cleanup), which locks every function, and schedules the first step. Steps: delete the WorkOS user (a missing user counts as done) and record when; delete in batches of 100 the person's memberships (writing a "left" event in each group), read states, unread rows, removal rows, typing rows, devices, reactions, uploads and reports they filed; delete the photo; and once an hour has passed since the WorkOS user was deleted (longer than any access token lives), replace the profile with the `deleted` tombstone. Each step is idempotent and each batch schedules the next in the same transaction. A cron every 10 minutes pages through every account still `deleting` and re-runs its current step, so a crashed or failed step resumes without the person. Re-running a step that is still going is harmless: the WorkOS deletion time is recorded once and never reset, and a "left" event is written only when a membership row is actually deleted. The typing cron pages through expired rows the same way. `profiles.setUp`'s internal mutation re-reads the profile by `authUserId` after the WorkOS check and refuses one that is `deleting`. WorkOS access tokens live 5 minutes by default; the dev and production WorkOS settings are checked to confirm the hour is longer. Their messages stay, attributed to "Deleted account". Group names generated from first names stay as group content.
- `reports.create({ messageId, reason })` → posts by others only; one report per person per message; keeps an excerpt of the text so deleting the message doesn't erase the evidence. Reports are reviewed in the Convex dashboard; how Q9 hears about a new report is still to be decided with Hasan.

## Sign-in endpoints (not Convex functions)

Settled in `build/auth-design.md`: the web Worker serves `/api/auth/*` for email code start and verify, Google and Apple redirects and callback, the phone's code exchange, token refresh (which also returns the sign-in method) and sign-out. Both apps call the same endpoints.

## Where v1 differs from the mock

These are accepted design changes; the mock checks they touch are judged against this list, not the original wording.

- Group info shows members' names and photos, not their emails. Anyone holding an invite link can join, so showing emails there would hand every member's address to whoever gets the link.
- Search (J7) matches whole words and the start of the last word typed, not text inside a word, and shows at most 10 matches per group and 50 in all.
- Finding people by name (J2) covers people who share a group with you; anyone else is found by exact email.
- An `@FirstName` mention notifies every member with that first name.
- Arrow-up (J6) edits the last own text post among the loaded messages.
- A reaction tooltip or sheet names at most 10 people per emoji, then "and N others".
- A person sees at most 20 removal notices in their group list.
- Reports are reviewed in the Convex dashboard; how Q9 hears about a new one is Hasan's call.
